# Lucky Pinball: Architecture Review & Rebuild Plan

Decisions are agreed (see §6). Scope: the current game in `Assets/Scenes/Pinball.unity` (the "Luck Number v0.3" ruleset: descending numbered enemies, flippers, a hand of element cards, lucky number, Q rolls, passive ball enchantments, active skills).
Note that `PROTOTYPE_BRIEF.md` and `ParameterGuide.md` (both now in `Docs/Archive/`) describe older versions ("mystery circles", special/bumper enemies, energy). The real design source is `Docs/LuckNumberPrototype.md`.

---

## 1. What exists today

| Area | How it works now | Files |
|---|---|---|
| Run flow, lives, score, hand, refill, lucky number, Q rolls, cast scheduling, telemetry, ball spawning, physics settings, debug cheats | All in one `GameManager` singleton | `GameManager.cs` (409 lines) |
| All tuning | `[Serializable]` classes embedded on the scene's GameManager | `GameTuning.cs`, `HudTuning.cs` |
| Enemies | Built at runtime from `CreatePrimitive(Cylinder)` + a second cylinder for the cap; materials cloned per enemy | `Enemy.cs` |
| Enemy movement | Static class, runs from `GameManager.FixedUpdate` | `EnemyMovement.cs` |
| Element effects | `Card.Equipment` enum (Arc/Spark/Shockwave) plus hard-coded ternaries in 6+ files | `Card.cs`, `EquipmentResolver.cs`, `SkillCast.cs`, `CombatVfx.cs`, `BallEnchantmentVisuals.cs`, `GameTuning.cs` |
| HUD | Entire Canvas built in code with legacy `Text`; layout exposed as ~200 numeric fields (`HudRefreshSlotsTuning`, `HudMakeTextTuning`, …) | `Hud.cs` (528), `HudTuning.cs` (238) |
| VFX | `LineRenderer` GameObjects created and destroyed per effect in code | `CombatVfx.cs`, `BallEnchantmentVisuals.cs` |
| Board | Generated by editor menu scripts; a procedural `[ExecuteAlways]` terrain mesh | `PinballSceneBuilder.cs`, `*Setup.cs`, `OuterRingSurface.cs` |
| Input | `Keyboard.current.aKey` etc. polled directly; the existing `InputSystem_Actions.inputactions` is unused | `Flipper.cs`, `GameManager.cs`, `Hud.cs` |
| Audio/VFX cues | New, clean `SfxCue` / `VfxCue` ScriptableObjects, but nothing in gameplay calls them | `Feedback/*` |
| Verification | ~15 editor menu "Check" scripts that drive play mode by hand | `Editor/*Check.cs` |

**Worth keeping:**
- The **rules themselves**: the Q-band math, burn/stun stacking rules, target snapshotting, refill debt. These are well specified and already checked.
- The **separate combat clock** (`CombatTime`, event-driven `TickGameplay`). It handles pause and launch-wait cleanly.
- **Kinematic flippers using `MoveRotation`**, continuous collision detection on the ball, and a 0.01 s fixed step.
- **`SfxCue` / `VfxCue`**. They are the right pattern, and the rest of the game should follow it.

## 2. Problems, ranked by how much they block human iteration

### 2.1 Nothing is a prefab. The look and feel lives in code
There are no `.prefab` files in the project. Enemies, the cap, the danger line, the spring coil, ball auras, every VFX, and the whole HUD are spawned by code. A designer or artist **cannot**:
- swap the enemy model, add an animation, or add a particle on death
- move a HUD element by dragging it (they have to edit `build.titlePosition` in a nested serialized class)
- attach an FMOD sound to "enemy killed" without writing code

`HudTuning` is the clearest symptom: it exposes *code layout parameters* (`HudRefreshEnemyLabelsTuning`, `HudMakeTextTuning`) instead of UI that can be edited directly.

### 2.2 The God object and the static singleton
Almost every class reaches into `GameManager.Instance`, which owns about 12 responsibilities. As a result:
- Nothing can be tested or reused in isolation. Enemies can't exist without a GameManager.
- Gameplay code calls the UI directly (`Hud.Instance.Popup` from `Enemy.TakeDamage`, `Hud.Instance.ShowCast` from `UseCard`). The HUD's static colour properties read back from GameManager, which makes a dependency cycle.
- Any change to the run flow means editing the same 400-line file, which causes merge conflicts in a team.

### 2.3 Content is code, not data
- **Elements**: adding a 4th element means editing the enum, `Card.Name`, `Card.Description`, `Card.SkillName`, `EquipmentResolver.BallHit`, `SkillCast.FireWave`, `LuckTuning.Plan`, `CombatVfx.ElementMaterial` (colours hard-coded by index), `BallEnchantmentVisuals`, and `shortCircuitUntil = new double[3]`.
- **The starting hand is hard-coded** in `GameManager.Awake`, and `handSize = 5;` silently overrides the Inspector value.
- **Lucky numbers 1–6** are hard-coded in `Card`, `Enemy`, `GameManager`, and `Spawner`.
- **Q bands** (−10 / 0 / 20 / 60 / 100) are hard-coded in `LuckTuning.MinResult`/`MaxResult`/`Plan`.
- All tuning sits on a **scene object**. There are no presets or difficulty variants, and every tuning change produces a scene-file diff.

### 2.4 Board geometry is duplicated and generated
The board shape lives in four places that must agree by hand:
- `SpawnTuning` (`boardHalfWidth`, `arcCenterZ`, `arcRadius`)
- `OuterRingSurface`
- `PinballSceneBuilder` constants
- `HudOverPlayfieldTuning`

Running "Build Scene" again throws away any hand edits. The launch point, danger line and spawn row are typed-in numbers (`launchLocal`, `dangerZ`, `normalSpawnZ`) instead of Transforms you can drag in the Scene view.

### 2.5 Input is hard-wired
Keys are polled directly, so the controls can't be rebound and there's no gamepad or touch support. The WebGL build exists, but mobile touch is impossible. "R" pauses, but the docs say it restarts.

### 2.6 Performance hazards that will grow with content
- `EquipmentResolver.Targets()` calls `FindObjectsByType<Enemy>()` and sorts the result. That happens every `TickGameplay` loop iteration, every `EnemyMovement.Step`, and **18× per ball hit** (via `Nearby`, 3 elements × 6 numbers).
- `SideReturnLane.DetectTrackContacts` calls `FindObjectsByType<Rigidbody>` every physics step, once per lane.
- `RefreshBallEnchantments()` (which also raises `HandChanged`) runs every fixed step.
- No pooling: VFX lines, popups and enemies are instantiated and destroyed constantly, and each enemy clones two materials.

### 2.7 Dead and legacy weight
Unused code and data still in the project. This is documented so it is **not ported**; it is not deleted from the old code (the old implementation stays untouched until cut-over):
- `Enemy.Kind.Special/Bumper`, `Energy => 0`, and the `EnemyTuning` fields `hitEnergy`, `pulseDamage`, `revealDuration`, `lifetime`, `kickSpeed`
- `CardTuning`, `SpecialTargetTuning`, `normalTargets` (values 28–296, but enemies only use 1–6)
- `BallReturnState` default `Capacity = 2`

Two docs were out of date: `PROTOTYPE_BRIEF.md` and `ParameterGuide.md`. Both are archived in `Docs/Archive/` (Phase 0).

### 2.8 No structure for a team
- Everything is in the global namespace.
- There are no assembly definitions, so every script edit recompiles everything, Odin and FMOD included.
- Verification uses custom editor menus instead of the Unity Test Framework, so it can't run in CI.

## 3. Recommendation: rebuild beside the old game

**Don't patch in place, and don't throw it all away.** Build a new structure in `Assets/_Project/` with its own scene, and port the *rules* into it piece by piece. Keep the old implementation (`Scripts/` and `Pinball.unity`) **completely unmodified** as the reference. It is deleted only after the new implementation has been tested against it and the team explicitly approves the deletion.

Reasons:
- About 70% of the current code is spawning, layout and visual construction, which prefabs replace outright. There's little worth refactoring in place.
- The rules (about 400 lines across `GameTuning`, `SkillCast`, `EquipmentResolver`, and the status code in `Enemy`) are valuable and port cleanly into plain C# classes.
- Having the old game side by side gives a feel reference for physics tuning, which no test can capture.

## 4. Target architecture

### 4.1 Guiding rules
1. **Prefabs own presentation. ScriptableObjects own numbers and content. Code owns rules.**
2. **Gameplay never calls UI, VFX or audio.** It raises events, and presentation listens to them.
3. **No `static Instance`.** One composition root wires the systems together, and everything else receives its dependencies.
4. **Anything spatial is a Transform or Collider in the scene**, never a typed-in coordinate.
5. **A new element, enemy type or wave needs a new asset, not a code change.**

### 4.2 Layers

```
┌────────────────────────────────────────────────────────────────────┐
│ Presentation (prefabs, UnityEvents, Animator, VFX Graph/Particles, │
│ FMOD cues, uGUI + TextMeshPro)                                      │
│   HudView · HandView · CardView · EnemyView · BallView · Popups     │
└───────────────▲────────────────────────────────────────────────────┘
                │ listens to events / reads read-only state
┌───────────────┴────────────────────────────────────────────────────┐
│ Gameplay systems (MonoBehaviours and plain C#, wired by GameContext)│
│   RunStateMachine · BallSystem · EnemySystem(+Registry) · Spawner   │
│   HandSystem · LuckSystem · CombatResolver · CastScheduler · Score  │
└───────────────▲────────────────────────────────────────────────────┘
                │ pure rule calls
┌───────────────┴────────────────────────────────────────────────────┐
│ Core rules (Pinball.Core asmdef, minimal UnityEngine use, unit-tested)│
│   QualityRoller · SkillPlanner · StatusRules(Burn/Stun) · RefillClock │
│   CombatClock · TargetSelection                                       │
└───────────────▲────────────────────────────────────────────────────┘
                │ reads
┌───────────────┴────────────────────────────────────────────────────┐

│   GameConfig · LuckConfig · DeckConfig · ElementDefinition[]         │
```

### 4.4 Data assets: what designers edit

**`GameConfig`** holds run-level settings:
- lives, drain cost, breach cost, launch countdown, kill score
- references to the other configs below

Physics settings (gravity, fixed step) move to **Project Settings**. Code should stop overwriting them in `Awake`.

**`DeckConfig`**:
- `startingHand: List<CardSpec>` (each is an element plus a number)
- `handSize`
- `drawTable`: element weights and number weights, so the draw is no longer `Random.Range` hard-coded
- refill interval and per-play delay

**`LuckConfig`**:
- number range (min/max, replacing the hard-coded 1–6) and refresh interval
- `bands: List<QualityBand>`, which replaces the −10/0/20/60 constants:
  ```csharp
  [Serializable] public class QualityBand {
      public string id;            // "Backlash", "Misfire", "Low", "Medium", "High"
      public Vector2Int qRange;    // e.g. (20, 59)
      public float normalWeight, luckyWeight;
      public BandOutcome outcome;  // ShortCircuit / Misfire / Cast
      public bool targetsAll;
  }
  ```

**`ElementDefinition`** is the key one. It replaces the `Card.Equipment` enum. Effects are polymorphic, using `[SerializeReference]` with Odin's drawer (Odin is already installed):

```csharp
[CreateAssetMenu(menuName = "Pinball/Element")]
public class ElementDefinition : ScriptableObject {
    public string displayName;        // "Arc"
    public string skillName;          // "Thunderstorm"
    [Multiline] public string descriptionTemplate; // "#{number} foes in {radius}m…"
    public Color color; public Sprite icon;

    [SerializeReference] public IPassiveEffect passive;  // runs on a valid ball hit
    [SerializeReference] public IActiveSkill   active;   // runs when a card is played
    [SerializeReference] public List<BandScaling> bandScaling; // targets/waves/durations per QualityBand

    public GameObject ballAuraPrefab;   // particle aura on the ball while held
    public VfxCue passiveHitVfx, activeHitVfx;
    public SfxCue passiveHitSfx, activeHitSfx, castSfx;
}
```

The effect classes are small, reusable modules, each with its own Inspector fields:
- `ChainDamagePassive` (radius, damage, `maxTargets(stack)` curve)
- `IgnitePassive`
- `StunPulsePassive`
- `WaveDamageSkill`
- `BurnSkill`
- `StunWaveSkill`

New element = a new asset that mixes existing modules. A new *kind* of behaviour = one new class. The ternary chains disappear.

**`EnemyDefinition`**:
- `prefab` (an `EnemyView` variant)
- health, radius, descend time, hit cooldown, score value
- unstick settings
- `numberRule` (random, or fixed)

Colours come from the prefab's materials, not from `Color` fields.

**`SpawnProfile`**:
- spawn interval, spawn chance, opening count
- a weighted list of enemies (`EnemyDefinition` + weight)
- an optional difficulty-over-time `AnimationCurve` for spawn interval and descend speed

Changing difficulty means swapping one asset reference.

### 4.5 Scene-authored geometry (replaces typed-in coordinates)

`Board.prefab` contains **hand-placed primitives** for walls, arcs, guides and the playfield. These are placeholders until the artist's meshes are ready. To make that swap painless, every piece follows the same structure:

```
WallL (prefab instance)        ← layer Board, BoxCollider, PhysicMaterial
 └─ Visual                     ← MeshFilter/MeshRenderer only; the artist replaces this
```

Nothing generates or rebuilds geometry. `OuterRingSurface` and `PinballSceneBuilder` are not ported. The flat-sides playfield the game currently uses is just a box plus a ramp primitive.

`Board.prefab` also has these named anchors, which code reads:

| Component | Replaces |
|---|---|
| `BallLaunchPoint` (Transform + gizmo arrow for direction and spread) | `launchLocal`, `launchBiasDegrees` |
| `SpawnZone` (a BoxCollider used as an area, or a Spline for the curved top; draws gizmos) | `normalSpawnZ`, `boardHalfWidth`, `arcCenterZ`, `arcRadius`, `HalfWidth()` |
| `DangerLine` (Transform + trigger; the visible red line is a child mesh) | `dangerZ`, `dangerLineScale/Offset/Color`, `MakeRedLine()` |
| `SpawnBlocker` (a collider on springs and lane outlets that spawn checks overlap) | `SpringBumper.BlocksSpawn`, `SideReturnLane.BlocksSpawn` |
| `ReturnLane` path as child Transforms (or the `com.unity.splines` package) | `Vector3[] path`, `outlet` |
| `PlayfieldArea` (a collider used to raycast card drops) | `HudOverPlayfieldTuning` |

Layers: `Ball`, `Board`, `Enemy`, `Flipper`, `Trigger`. Set them up in the physics collision matrix and stop checking `CompareTag("Player")` everywhere.

### 4.6 Gameplay systems

| System | Responsibility | Replaces |
|---|---|---|
| `GameContext` (composition root, one per scene) | Holds config refs and scene refs; creates and wires the systems in a known order; exposes the run's state read-only | `GameManager.Instance`, `Start()` that `AddComponent`s things |
| `RunStateMachine` | States `Launching → Playing ⇄ Paused → GameOver`; owns lives; raises `RunStateChanged`, `LivesChanged` | `RunState`, `LoseLives`, `BeginWaiting`, `Restart` |
| `CombatClock` | Gameplay time that only advances while Playing; schedules timers (`Schedule(time, callback)`) | `combatTime`, the hand-written `next = Min(...)` loop |
| `BallSystem` | Pooled balls, launch, drain, multi-ball list | `CreateBall`, `LaunchBall`, `OnDrain`, `ballTemplate` |
| `EnemyRegistry` | Enemies register in `OnEnable` and unregister in `OnDisable`; keeps a sorted list (front first); `QueryNearby(point, r, filter)` | every `FindObjectsByType<Enemy>` |
| `EnemySpawner` | Reads `SpawnProfile` + `SpawnZone`; pooled instantiation | `Spawner.cs` |
| `EnemyMarch` | Queued descent toward the `DangerLine` | `EnemyMovement.cs` |
| `HandSystem` | Hand slots, draw, refill debt; events `CardAdded/Removed/Shifted` | hand code in GameManager |
| `LuckSystem` | Current number, refresh timer, Q roll (via Core `QualityRoller`), debug overrides | `currentNumber`, `NextOutcome`, `Debug*` |
| `CombatResolver` | Valid ball hit → base damage → run each held element's `IPassiveEffect` | `EquipmentResolver.BallHit` |
| `CastScheduler` | Active skill waves on `CombatClock` | `casts` list, `SkillCast.FireWave` |
| `ScoreSystem` + `RunStats` | Score, multi-kill tracking, telemetry | `score`, `OnNormalKill`, `RunTelemetry` |

Enemy prefab components:
- `EnemyHealth` (HP, damage, death)
- `EnemyStatus` (burn/stun via Core `StatusRules`)
- `EnemyContact` (ball-hit cooldown, unstick nudge)
- `EnemyView` (presentation)

### 4.7 Events: the main hook for designers

Use two levels:
1. **Code events** for systems talking to each other, e.g. plain C# events on the systems: `EnemyHealth.Damaged(DamageInfo)`, `HandSystem.CardPlayed(CastResult)`.
2. **Inspector hooks on prefabs**: each view component exposes `UltEvent`s, so designers drag in an `SfxPlayer`, `VfxPlayer`, `Animator.SetTrigger`, or a camera shake with no code. UltEvents (unlike `UnityEvent`) can call static methods and methods with several parameters, and can pass event data such as the hit position on to the listener:

```csharp
public class EnemyView : MonoBehaviour {
    [SerializeField] TMP_Text numberLabel;
    [SerializeField] Image healthFill;
    [SerializeField] Renderer body;
    [Header("Hooks")]
    public UltEvent<Vector3> onHit;   // hit point
    public UltEvent onKilled, onBreach, onBurnStart, onBurnEnd, onStunned, onTargetPreview;
}
```

Do the same on `BallView` (`onLaunch`, `onDrain`, `onFlipperHit`), `FlipperView` (`onFlip`), `SpringBumper` (`onKick`), and `HudView` (`onLuckyNumberChanged`, `onCardDrawn`, `onGameOver`). This is where the existing `SfxCue`/`VfxCue` system plugs in.

3. **ScriptableObject event channels**, only where they're needed: global events that many unrelated listeners need, such as `RunStateChanged`, `LuckyNumberChanged` and `GameOver`. UI, audio (for example FMOD global parameters) and analytics subscribe through an asset reference instead of a scene reference. Prefab-local things like an enemy being hit stay on that prefab's UltEvents.

### 4.8 UI

- Build the HUD as **prefabs in the Canvas** (uGUI + TextMeshPro). Layout is done with anchors and layout groups in the editor, so `HudTuning` disappears entirely.
- Split it into small presenters:
  - `TopBarView` (score, lives, time, lucky number)
  - `HandView` + `CardView` (drag uses `IBeginDragHandler`/`IDropHandler` from the EventSystem, not manual mouse polling)
  - `CastResultView`
  - `EnemyLabelView` (a world-space label or overlay follower, pooled)
  - `PopupView` (pooled)
  - `PauseMenu`, `GameOverView`
- Presenters only subscribe to system events and read state. They never change game state except through explicit commands (`hand.TryPlay(slot, dropPoint)`).
- Colours live in a `UiTheme` ScriptableObject, or in TMP styles and colour presets. Remove the static colour properties.
- UI Toolkit is an option, but uGUI is easier for a mixed team to edit by eye and works with the existing world-space labels. Recommendation: **uGUI**.

### 4.9 Input

- Use `InputSystem_Actions.inputactions` with a `Gameplay` map (`FlipLeft`, `FlipRight`, `Pause`, `Restart`, `Nudge`?) and a `UI` map.
- Flippers get an `InputActionReference` field, so rebinding and adding gamepad support are data changes.
- Add on-screen touch zones for WebGL and mobile through the same actions.

### 4.10 VFX and pooling

- Replace the code-built `LineRenderer` effects with prefabs (Particle System or VFX Graph, or LineRenderer prefabs with an animation script), played through `VfxCue`.
- Add pooling to `VfxCue` itself using `UnityEngine.Pool.ObjectPool`, keeping the same API so callers don't change.
- Pool enemies, popups and labels as well.
- Use `MaterialPropertyBlock` for per-enemy tints instead of cloning materials.

### 4.11 Debug and tuning tools

- A **runtime debug panel** (an Odin `[Button]` group on a `DebugCheats` component, or a simple IMGUI overlay compiled only into `DEVELOPMENT_BUILD`) for setting the lucky number, forcing the next Q, adding a card, spawning an enemy, and toggling god mode. This works in builds too, not just through `GameManagerEditor`.
- Use Odin `[ValidateInput]`/`[InfoBox]` on configs to catch bad data early (band ranges that overlap, all weights zero).
- Use `OnDrawGizmos` on spawn zones, launch point, danger line and lane paths.

### 4.12 Tests

- **EditMode** (`Pinball.Core`): port `CardMathCheck`, `LuckPrototypeCheck`'s rule cases, and `TuningCheck` to NUnit tests for `QualityRoller` distributions, `SkillPlanner` rounding, burn/stun stacking, and refill debt. Inject the random source (`IRandom`) so tests are deterministic.
- **PlayMode**: a small test scene that checks the ball can't tunnel through flippers, a drain costs a life, a hit damages and kills an enemy, and pause freezes the combat clock.
- Run both headless with `-runTests` once CI exists.

## 6. Decisions (agreed)

| # | Topic | Decision | What it changes in this plan |
|---|---|---|---|
| 1 | **Board geometry** | **Hand-placed primitives for now; the artist's meshes replace them later.** No generator scripts and no procedural runtime mesh. **Exception (agreed in Phase 3):** the playfield surface (plateau + entry ramp) is one saved mesh asset with a MeshCollider, copied from the old generated surface, because box joints measurably changed the ball's path. | Every board piece is a prefab with a **`Collider` root and a separate `Visual` child**. The artist swaps the `Visual` mesh without touching the physics. `OuterRingSurface` and `PinballSceneBuilder` are not ported (§4.5). |
| 2 | **Events** | **C# events between systems, [UltEvents](https://kybernetik.com.au/ultevents/) for Inspector hooks on prefabs, and ScriptableObject event channels only where a global event needs listeners in many unrelated places.** | `UnityEvent` hook fields in §4.7 become `UltEvent`. UltEvents 3.1.1 is installed as an embedded package (`Packages/com.kybernetik.ultevents`). |
| 3 | **UI** | **uGUI + TextMeshPro.** | As described in §4.8. |
| 4 | **Odin** | **Yes: runtime data may depend on Odin.** | `[SerializeReference]` effect lists use Odin's type picker. Odin validation attributes go on configs, and debug buttons use `[Button]`. |
| 5 | **Design scope** | **Rebuild what is currently in the engine (Luck Number v0.3).** The "mystery circles" brief is out of scope. | No reveal module. `PROTOTYPE_BRIEF.md` is archived in Phase 0. The source of truth is the live code plus `Docs/LuckNumberPrototype.md`. Where the two differ, the code wins. |
